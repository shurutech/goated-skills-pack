# Alembic migrations and schema patterns

> Written from a real multi-tenant FastAPI + Postgres codebase. Names, fixtures, paths and commands are examples: map them to your repo before following them literally.

Read this before touching a model or generating a migration. The project's own
`<schema patterns doc>` and `design-rules.md` are the source of
truth — this file is the working checklist and the reasoning behind it.

---

## 1. The migration decision

Most schema-shaped requests don't need a migration. Work through this before
generating one.

**Does the data need a column at all?** The standard mixin stack includes a
JSONB extension column precisely so ad-hoc, rarely-queried attributes don't each
cost a migration. Use it for that — and don't use it for structured data you
will filter, sort, or join on, because you can't index it usefully and every
reader has to guess the shape.

**Can an in-flight migration absorb the change?** Before generating anything:

```bash
docker exec <backend container> alembic current      # note the head revision
ls alembic/versions/
git log --oneline alembic/versions/                # anything unmerged on this branch?
```

If a migration on your branch isn't merged yet and touches the same table,
**edit that migration** instead of stacking a second one. Two migrations that
add two columns to one table on one branch is sprawl: it makes the rollback
path longer, the review noisier, and the history harder to read. The exception
is when the first migration has already run on a shared environment — then
amending it means that environment silently never gets your change, so add a
new one and say why.

**Is it a core table?** The design rules name roughly a dozen tables that every
module, token, and entitlement snapshot depends on — organizations, users,
memberships, roles, permissions, plans, subscriptions, the main domain entities, and the
join tables around them. Any column, index, or constraint change on one of them
requires an architectural decision record in your ADR log, written in the **same
change** as the migration and the model edit. A reviewer cites the record number
when approving. This is not a follow-up task.

For non-core tables, a short note in the migration of what it's for is enough —
and this is one of the two places the repo's rules override the general
no-comments preference.

## 2. Writing the migration

**Naming and chaining.** `<revision>_<verb>_<thing>.py`. The `revision` and
`down_revision` fields form one linear chain with no branches. If two people
generate migrations from the same head, one has to rebase theirs onto the
other's — a branched chain will fail to upgrade.

**The downgrade has to actually work.** An autogenerated downgrade that drops
a table is fine. One that silently loses data, or that doesn't reverse what the
upgrade did, is worse than no downgrade at all — because someone will run it
under pressure. Test it: `alembic upgrade head`, then `alembic downgrade -1`,
then `alembic upgrade head` again.

**Autogenerate is a first draft, not the output.** Always read the generated
file. It routinely misses server defaults, gets index conditions wrong, drops
things it shouldn't because a model isn't imported, and cannot know what to do
about existing rows.

**Adding a NOT NULL column to a populated table is three steps, not one.** Add
it nullable, backfill the existing rows, then set NOT NULL. A single-step
`add_column(nullable=False)` without a server default fails immediately on any
table with data in it.

**Data migrations must be safe to re-run.** Use `ON CONFLICT DO NOTHING`, or
check for the row first. Migrations get re-run in practice — a failed deploy
halfway through, a restored environment, a developer's local database in an odd
state.

**Deploys overlap migrations (expand, then contract).** Old pods keep serving
while the migration runs and until they roll over. So a change that breaks the
old code (dropping or renaming a column, tightening a type) ships in two
releases: expand (add the new column or table, write both) then, after every old
pod is gone, contract (drop the old). A rename is add, backfill, switch, drop,
never `alter_column(new_column_name=...)` in one step. Autogenerate emits a
rename as a drop plus an add and loses the data; rewrite it by hand.

**Locks.** Any DDL that takes a heavy lock queues behind a long transaction and
blocks everything behind it. Start such a migration with
`op.execute("SET LOCAL lock_timeout = '5s'")` (reuse an existing migration in your history as the
precedent if there is one) so it fails fast and can be retried rather than stalling
traffic. Creating an index on a populated table blocks writes: use
`CREATE INDEX CONCURRENTLY`, which cannot run in a transaction, so wrap it:

```python
with op.get_context().autocommit_block():
    op.create_index("ix_t_c", "t", ["c"], postgresql_concurrently=True)
```

Adding NOT NULL to a big table: add the column nullable, backfill in batches (one
statement per batch, not one giant UPDATE), then constrain; a CHECK added `NOT
VALID` and then `VALIDATE`d avoids a long full-table lock. Say in the PR when a
migration needs a window.

## 3. The mixin stack

Compose in the project's declared order, because the declaration order is the
column order in the migration:

```python
class MyTable(
    UUIDPrimaryKeyMixin,    # id
    TenantScopedMixin,         # organization_id NOT NULL, FK to organizations.id
    TimestampMixin,         # created_at, updated_at
    SoftDeleteMixin,        # deleted_at, nullable + indexed
    AuditMixin,           # created_by_user_id, updated_by_user_id
    ExtraDataMixin,          # extra_metadata JSONB
    SQLModel,
    table=True,
):
    __tablename__ = "my_table"
```

Primary key first so it leads the table; the organization column next so the
multi-tenant filter is impossible to miss when reading the model; soft-delete
and audit columns trail.

**The database owns generated values, not Python.** The id defaults to
`gen_random_uuid()` server-side, and the timestamps default to
`CURRENT_TIMESTAMP` with `updated_at` carrying an `onupdate`. Don't set any of
them in Python — if you do, the value differs depending on which code path
inserted the row (endpoint vs. fixture vs. data migration), and the drift is
invisible until something compares timestamps.

**Mixins declare columns with `sa_type` plus `sa_column_kwargs`, never
`sa_column=Column(...)`.** A `Column` object can only belong to one table, so a
shared mixin using `sa_column` breaks the second model that inherits it. Follow
the existing mixins' style exactly.

**Overriding a mixin field needs a documented reason.** There are real
precedents in a typical multi-tenant schema — a role table where system-level rows legitimately
have no organization, an intake table that tolerates a null organization until
a matching step runs. Both are recorded in the decision log. If you need a
third, it needs the same treatment, not a silent override.

## 4. Soft delete

`deleted_at IS NULL` means the row is live. Two consequences that get forgotten:

**Every list query filters it out.** `.where(Model.deleted_at.is_(None))`. A
list endpoint that skips this shows deleted records back to the user, which
reads as data resurrection.

**Uniqueness must ignore deleted rows.** A plain unique constraint on
`(project_id, user_id)` means once a member is soft-removed, they can never be
re-added. The pattern is a partial unique index:

```python
__table_args__ = (
    Index(
        "uq_<table>_<cols>_active",
        "project_id",
        "user_id",
        unique=True,
        postgresql_where=text("removed_at IS NULL"),
    ),
)
```

and the migration declares the identical condition:

```python
op.create_index(
    "uq_<table>_<cols>_active",
    "team_members",
    ["project_id", "user_id"],
    unique=True,
    postgresql_where=sa.text("removed_at IS NULL"),
)
```

**Declared in both places or it's a bug.** The model's table arguments and the
migration have to agree. Only the migration means a fresh database built from
the models lacks the index. Only the model means the running database lacks it —
and that's the one where duplicates actually get in.

Bulk inserts into these tables use the Postgres-specific insert with
`on_conflict_do_nothing`, passing both `index_elements` and the matching
`index_where`, or the conflict target won't match the partial index.

Hard delete is reserved for deliberate cascade cleanups, where removing a parent
must remove its children.

## 5. Org scoping

The mixin guarantees the column is there and NOT NULL. **It does not filter
anything.** Every query in the service layer must add
`.where(Model.organization_id == ctx.organization_id)` — including when a
foreign key seems to make it redundant, because a foreign key to a row in
another organization is exactly the bug you're guarding against.

Two independent layers, on purpose: the schema makes an unscoped row
impossible, and the service makes an unscoped read impossible. Neither one
covers for the other being missing.

## 6. Status columns

Status is `String(32)` plus a Python `Enum`, with the server default set to the
enum member's `.value` — not a Postgres enum type:

```python
status: ItemStatus = Field(
    default=ItemStatus.ACTIVE,
    sa_column=Column(
        String(32),
        nullable=False,
        server_default=ItemStatus.ACTIVE.value,
        index=True,
    ),
)
```

Postgres enums need an `ALTER TYPE` in its own transaction to add a value,
which makes a routine "add one more status" into an awkward migration. A string
column extends for free.

## 7. Encrypted columns

The project's encrypted string type stores values with AES-GCM and a versioned
key prefix. Use it for OAuth access and refresh tokens, webhook secrets, and
client secrets — anything that would cause harm if a database backup leaked.

**You cannot query by an encrypted value.** No `WHERE`, no index lookup, no
join. So never use it on an identifier you need to search by; keep a hashed
column alongside if you need lookup, and encrypt only the secret itself.

## 8. Naming

- Tables: snake_case, plural — `memberships`, `team_members`.
- Columns: snake_case — `organization_id`, `assigned_to_user_id`.
- Indexes: `ix_<table>_<columns>`, or `uq_<table>_<columns>[_active]` when
  unique.
- Foreign keys: `<thing>_id` referencing `<table>.id`.

---

## 9. Where a new module's files go

A top-level resource is a sub-package of `app/modules/` owning its `models.py`,
`service.py`, `schemas.py`, `router.py`, and `admin.py`. Its router declares the
top-level prefix, and gets mounted in the versioned API router.

A sub-resource — rows that hang off a parent, like members, rooms, milestones,
documents — lives in a **sub-package inside the parent module**, with its own
models, service, and router. The sub-resource router declares the full nested
path and is included by **the parent's router**, not by the top-level API
router.

The payoff: adding a sub-resource touches no files outside the parent module's
own directory, plus one `include_router` line. If your change is editing the
top-level API router to add a nested path, the file is in the wrong place.

## 10. Checklist

- [ ] Confirmed a migration is genuinely needed, and said why out loud
- [ ] Checked `alembic current` and the versions directory for an in-flight
      migration that should absorb this change
- [ ] Decision record written in the same change if a core table is involved
- [ ] Read the autogenerated file line by line; fixed server defaults and index
      conditions it got wrong
- [ ] Existing rows handled — nullable, backfill, then NOT NULL, where needed
- [ ] Data changes are safe to re-run
- [ ] Downgrade tested by actually running down and back up
- [ ] Breaking change split into expand and contract; `lock_timeout` set; index on a
      populated table built `CONCURRENTLY` inside `autocommit_block()`
- [ ] Mixins composed in the project's order; nothing overridden without a
      documented reason
- [ ] Partial indexes declared identically in both the model and the migration
- [ ] Status columns are string plus Python enum, with a server default
- [ ] Encrypted type used only on secrets, never on anything queried
- [ ] Knowledge base index updated if a new file was added
